## feat: generate Siri AI tool intents and app skills from Dart - Standard

## Overview

Apple's Siri AI Developer Preview (iOS 27.3 betas, 2026-11-03) lets Siri:

- call an app's App Intents as **tools**,
- fill **generable entities** from what a person says,
- follow **app skills** written as `SKILL.md` files.

None of that goes through Foundation Models, the framework this package wraps. It is compiled Swift that Xcode reads from the app target at build time.

This plan does two things:

1. **Explain the boundary.** Add a "Siri AI vs this package" section to the `native_ai_bridge` README. The package runs your prompts on Apple's models; Siri AI tools need Swift App Intents in the app target.
2. **Remove the Swift boilerplate for Flutter developers.** `native_ai_bridge_generator` gets a standalone, pigeon-style CLI: `dart run native_ai_bridge_generator:siri`. It turns experimental Dart annotations into:
   - Swift `@AppIntent(.tool)` intents,
   - `@AppEntity(.generable)` entities,
   - one Swift handler protocol per tool, which the app implements,
   - validated `SKILL.md` files.

## Problem Statement / Motivation

- **Wrong assumption.** Users will assume a "native AI bridge" can register Siri tools from Dart. It can't, because App Intents are found at build time. The README should say so before people try.
- **Silent failures.** Flutter teams adopting Siri AI must hand-write Swift intents with exact metadata: a title and description on every intent and parameter, and only allowed types on generable entities. They must also hand-write `SKILL.md` files under strict rules. Mistakes fail silently: a broken skills bundle simply provides no skills.
- **Stale generator.**
  - It pins `native_ai_bridge: ^0.1.0` while the plugin is at 0.2.1.
  - Its links point at a repository that doesn't exist.
  - `lib/src/tool_generator_builder.dart` is dead code, yet the package's barrel file still exports it.
  - It uses `analyzer ^6` and `source_gen ^1.5`.
  - It dev-depends on Flutter despite being pure Dart.
  - Its `.dart_tool/` and `pubspec.lock` are committed even though `.gitignore` lists them.

## Proposed Solution

### Decisions

| Topic | Decision |
|---|---|
| Delivery | A standalone CLI, not build_runner. build_runner derives output paths from input paths and can't write into `ios/`. pigeon, `flutter_launcher_icons` and `flutter_native_splash` all use a CLI for native output. The existing `.tool.g.dart` builder is unchanged. |
| Annotations | Four, in `native_ai_bridge`, marked `@experimental` (direct `meta` dependency): `@SiriTool(title, description)`, `@SiriField(title, description)` for tool parameters and entity properties, `@SiriGenerableEntity()`, and `@SiriSkill(name, description, body)`. The reader matches them with `TypeChecker.fromUrl`, so the generator doesn't import plugin code. |
| `perform()` | Native only. Each tool's `perform()` calls a generated Swift protocol `<Tool>Handler` through its static `shared` property, which the app sets at launch. No Flutter engine is needed, and it works with the app killed. Open-app and headless-engine modes are non-goals. |
| Xcode | The CLI never edits `project.pbxproj`. It writes into the configured folder and warns if that folder doesn't exist. The README explains how to add the folder as a synchronized group and how to create the skills bundle once in Xcode (File > New > Skills Bundle). |
| SDK gating | Generated Swift is `@available(iOS 27.3, *)`. A compiler-version check can't tell Xcode 27.1 from 27.3, because both ship Swift 6.4. The single optional config key `compilation_condition` (for example `SIRI_AI_TOOLS`) wraps every generated Swift file in `#if <condition>`, and the README shows how to set it only for Xcode 27.3 builds. |
| Header | Every generated file starts with a fixed line: `// GENERATED by native_ai_bridge_generator. Do not edit.` (an HTML comment in `SKILL.md`). There is no version or hash, so goldens don't churn between releases. The CLI only overwrites files that carry this header. |
| Versions | `native_ai_bridge` 0.2.2 adds the annotations and the README section. `native_ai_bridge_generator` 0.2.0-dev.1 is breaking: the removed export and the dependency upgrade. It's a pre-release while Apple's API is in preview. Publishing is a separate release step that needs the owner's go-ahead. |

### Config (`native_ai_bridge.yaml` at the app root)

```yaml
siri:
  input: lib/siri/siri_tools.dart
  swift_out: ios/Runner/Siri/Generated
  skills_out: ios/Runner/Skills.skillsbundle/Skills
  compilation_condition: SIRI_AI_TOOLS
```

If the config is missing, the CLI exits 2 and prints this example.

### Output

- **Tools:** `<swift_out>/<Tool>.g.swift` holds an `@AppIntent(.tool)` struct with a `title`, an `IntentDescription`, and `@Parameter(title:description:)` on every field. It also holds the `<Tool>Handler` protocol and the call through `<Tool>Handler.shared`.
- **Entities:** `<swift_out>/<Entity>.g.swift` holds an `@AppEntity(.generable)` struct over `TransientAppEntity` with `@Property(title:description:)` fields.
  - Allowed types: `String`, `int`, `double`, `bool`, `DateTime`, an annotated enum (mapped to `AppEnum`), another generable entity, or a `List` of these.
  - Any other type is a generation error.
- **Skills:** `<skills_out>/<name>/SKILL.md` holds frontmatter with only `name` and `description`, then the body. The folder name always comes from `name`.
- **Single source for Apple's names:** every Apple macro and type name lives in `apple_templates.dart`, so a preview rename is a one-file change.

### Commands

- `dart run native_ai_bridge_generator:siri` writes the files.
- `dart run native_ai_bridge_generator:siri --check` writes nothing. It exits 1 and lists every stale, missing or orphaned file, where an orphan is a headered `.g.swift` the current input no longer produces. Orphans are deleted by hand. Meant for CI.

### Validation errors (each names the Dart source location; no stack traces)

| Code | Rule |
|---|---|
| `skill-name` | 1-64 characters from `[a-z0-9-]`, no leading or trailing hyphen, no `--`. Two skills with the same name are a path clash and fail here too. |
| `skill-description` | Required, a single line, at most 1024 characters. |
| `skill-body` | At most 10,000 characters, Apple's documented limit. |
| `tool-metadata` | A title and a description on the tool and on every parameter. |
| `unsupported-type` | A map, record, `dynamic`, or nullable list in a tool parameter or generable entity. |

## Technical Considerations

- **Architecture.** Three pure layers, each tested on its own:
  - The reader: the analyzer resolves the input library into a `SiriManifest`.
  - The renderers: `SiriManifest` in, `Map<path, String>` out.
  - The writer: diff, write, check.

  The CLI is `run(List<String> args) -> Future<int>`, tested in-process without spawning a process.
- **Dependencies.**
  - Use an analyzer range that spans majors (as pigeon does) and resolves together with a Flutter app on analyzer 13.x. The Mataa app resolves 13.3.0.
  - Moving the existing builder off analyzer 6 means migrating to the new element model. That is real work, kept in Phase 1.
  - The generator moves to `test` and `very_good_analysis`, and drops `flutter_test` and `flutter_lints`.
  - The CLI adds `args`, `yaml` and `path`.
- **Local development.** The generator uses `dependency_overrides: native_ai_bridge: path: ../native_ai_bridge` while 0.2.2 is unpublished. At release it constrains `^0.2.2` and the override is removed. The example uses the same override, which also fixes its old `pub get` failure.
- **Analysis.** Fixtures that are meant to fail validation are excluded in `analysis_options.yaml`. Generated Swift isn't Dart, so it isn't analyzed.
- **Compatibility.** `GenerateTool` output is unchanged, and the existing generator tests are the baseline.
- **Security.** Generated code never embeds secrets, and handlers receive only values. The README tells apps to set `authenticationPolicy` on any tool that changes state.
- **Not verifiable in this repo.** Siri behaviour needs a physical Apple Intelligence iPhone on iOS 27.3, and Apple's preview API may change between betas.

## Dependencies & Risks

- **Apple preview churn.** Names such as `@AppIntent(.tool)`, `@AppEntity(.generable)`, `TransientAppEntity` and the skills bundle rules may change. They are kept in one template file, the annotations are `@experimental`, and the generator ships as a pre-release.
- **Unverified Apple details.** Two are unconfirmed: whether optionals and `double` are accepted in generable entities, and whether skills inside a CocoaPods plugin framework get indexed. Output targets the app only; optionals are rejected until a 27.3 compile proves otherwise.
- **Analyzer migration.** Moving the existing builder from analyzer 6 is the riskiest step. It goes first, alone, with the existing tests as the baseline.
- **Toolchain.** Typechecking needs the Xcode 27.3 beta installed beside the current Xcode, used only through `DEVELOPER_DIR`.
